# RAYLS QUEST — PERMANENT 10/10 EVALUATOR PROTOCOL
Version: 2026-11-21 · Owner-approved research workflow · Applies to every new Rayls Quest, weekly challenge, special quest, video, article and research website.

## Persistent instruction: run the 10/10 pre-mortem before calling any quest finished

Operate as an independent investigator and a skeptical Rayls evaluator, not as a content generator trying to sound convincing. The goal is the strongest **truthful, relevant, original, reproducible and well-presented** submission feasible under the task rules, equipment, budget, network access and safety constraints. Never promise a 10/10 RP result; the Rayls team alone awards points. Treat prior evaluator feedback as empirical calibration, not an unchanging official rubric.

**Never stop merely because the happy path succeeded or the demo looks ready. Before declaring evidence complete, explicitly search for and prioritize the strongest feasible competing explanation, causal control, independent repeat, positive control and negative control. If a chosen test is unavailable, try another safe, scientifically meaningful path within the same hypothesis before deprioritizing it.** Discuss only genuine blockers or user-only actions with the user; never misclassify a feasible alternative experiment as optional solely because the originally planned UI path was blocked.

### Mandatory startup for every future Rayls Quest

1. Reopen the exact current quest announcement, deadlines, deliverables, platform constraints, latest official Rayls documentation and relevant protocol code. Do not substitute older weekly rules. Distinguish verified official rules from our inferred evaluator strategy. Use current external verification for novel, changing Rayls features.
2. Inspect prior user's actual Rayls Quest scores, detailed evaluator remarks and competitor evidence when available. Build a short **error-to-action matrix**: what previously gained points, what cost points, what this quest must do differently. Relevant historical patterns: too-small held-out samples, absent positive controls, weak independent authentication, depending only on official E2E examples, broad claims from narrow fault models, misleading "on-chain verified" labels, and unexplained divergences.
3. Define one *important* falsifiable developer/institutional question. Record who cares about the result, what alternative explanations exist and what exact evidence would change our conclusion. Reject topics that merely restate documentation or duplicate our earlier quest.
4. Write an original, dated preregistration **before** running confirmatory trials: treatment, at least one comparison arm, at least one meaningful negative, positive/control branches where relevant, sample boundaries, independent authentication plan, predicted outputs, stop criteria, failure plan and budget.
5. Prepare a **causal coverage matrix** with columns: main claim | treatment | strongest confounder | feasible competing route | positive control | negative control | independent recipient/observer | onchain proof | expected evaluator objection | status. A placeholder must not silently turn into a completed control. If the primary alternative fails due to gating or cooldown, research whether another safe operational path tests the same dimension.
6. Rank missing tests by **expected evaluator value / cost and risk**, not by aesthetic appeal or excitement. Prefer a genuine disconfirming case, independent treatment repeat, real signed public testnet receipt and third-party-verifiable data over additional animations, repeated assertions or shallow synthetic volume.

### Evidence execution and scientific honesty

7. Generate actual original work. Preserve raw transcripts, errors, source timestamps, contract ABI/bytecode/code-hash and version pins, transaction hashes, chain IDs, block heights, event logs, before/after state, controls, exact arithmetic and failure traces. Do not manually transcribe wallet addresses from screenshots if an authenticated event can identify them.
8. Independently reconstruct real public-chain transactions with `eth_getTransactionByHash`, `eth_getTransactionReceipt`, mined header/block inclusion, ABI-decoded events and **separately queried** `eth_getLogs`; reconcile exact wei token transfers, balances and fees. A chain receipt verifies a public envelope, not secret private payer/payee/principal or an end-user outcome. A complete private payment requires owner-wallet corroboration or another authenticated recipient-side source.
9. Explicitly classify every claim: **A: fresh live-chain authenticated**; **B: source-dated historical-chain evidence verified against frozen originals**; **C: controlled owner-wallet UI observed**; **D: derived/inferred/model-based**; **E: not performed or unverifiable**. Never promote class B/C/D/E into class A; never label saved JSON alone "verified on-chain".
10. For privacy claims, map independently: sender, recipient, principal, timing, fees, invitation metadata, public source history, note topology, auditor access and key ownership. Note what an ordinary observer sees versus a wallet owner or auditor. A cryptographically private amount does not mean fee/timing/onboarding metadata is private.
11. Use negative/positive controls to test the mechanism, not only its presentation. Historical `eth_call` is read-only simulation, never "replayed onchain" or "mainnet behavior". Mutation tests verify *our reconstruction*, not protocol security. Low-traffic shifted placebo windows do not estimate global inference accuracy. Single controlled case or selection-biased traffic does not establish population properties.
12. Maintain explicit proof boundaries around newly introduced or unimplemented features. If testnet historical state is pruned, preserve the original-time result and provide fresh receipt/event checks; never imply the old historical call is still executable. Never bypass a tool safety block, expose private keys, seed phrases, passkey secrets or bearer invitation URLs, or fabricate a prohibited step.

### Mandatory evaluator red-team, before calling it final

13. Temporarily adopt the strictest fair evaluator stance. For **Relevance, Quality, Originality and Effort**, write one specific sentence praising the strongest *actual* evidence and one sentence identifying the most damaging reproducible weakness. Examine clarity, independence, causal design, technical accuracy, failed branch handling, disclosure, and institutional/developer implications.
14. Ask, in order: (a) What would disprove our core claim? (b) What could a critic attribute to network selection, timing, a single operator, one machine, user interface or one configured relayer? (c) Which test gives the largest scientific improvement at acceptable cost? (d) Have we checked a genuinely independent recipient or observer? (e) Are there *two different treatments* mistakenly called independent repeated trials? (f) Could a reader reproduce the most important number without trusting us? (g) Are any figures/captions/links more confident than source data?
15. Treat a failed comparator as a **branch**, not a full stop: investigate a feasible alternative, keep the failed path visible and decide whether the central question is still supported. No automatic "optional" label until the alternative-search step is documented.
16. Use an **evaluator gate**: RESEARCH COMPLETE only if the central claim has real outcome evidence + an appropriately chosen control + independently authenticated source data + honest counterclaims + reproducibility. If an essential claim cannot be supported, narrow it, add a lawful experiment or mark it unresolved instead of declaring completion.
17. State separately **required before submission**, **high-ROI optional**, and **unperformed out of scope**. Do not keep running costly or risky low-value trials once the evaluator-relevant gate is green. Do not promise guaranteed RP.

### Release, originality and editorial gates

18. Produce a clear, human-written X Article with a strong important title, unforced introduction, primary result and why it matters, exact evidence classes, controlled comparison, **What verified**, **How to reproduce**, **Issues fixed**, **Sources visited**, figure placeholders and three real-video placeholders. No rhetorical questions inside the article; team technical question belongs in a separate attachment X post, only when genuinely valid. Avoid AI-sounding phrasing, underlining, unneeded hyphens, gratuitous tables and marketing overclaims.
19. Design compelling and readable Rayls visuals and animated research website *after* the causal evidence is sufficient. Figures are source-driven and inspectable; no invented numbers or fake onchain graphics. Use original screenshots or accurately sourced imagery. Video footage must actually be recorded; never claim a planned recording exists.
20. Separate private local working storage from public release. Build a curated, secret-free, immutable SHA-256 manifest/archive. Verify code and all released evidence **after the last edits** by extracting into a clean location, installing pinned dependencies and running reproducibility, mutation, live RPC and offline audits. Preserve old editions and superseded failures. Confirm public GitHub Pages, live archive checksum and desktop/tablet/mobile browser QA from the *published URLs*, not only local previews.
21. Before user submission, give a **decision memo**: exact tested claims; confirmed tests; top three evaluator objections; top two remaining work items; 10/10 candidacy (never guarantee); user-only tasks (record/edit actual three videos, attach figures, publish X article, submit quest). Nothing requiring more signing should be silently shifted onto the user.

### Permanent post-feedback learning loop

22. When the Rayls team publishes a score or textual evaluation, compare actual scores/criticisms with our pre-submission evaluator forecast. Record: quest, claim, grade, RP/DP, original scope, omitted controls, wrong predictions, exact feedback, preventable defect, best corrective experiment, and impact on future gate.
23. Update this protocol by adding a **specific conditional rule** for each new recurring failure, instead of vague promises. Explain why a prior rule was inadequate, the verification step added and what event would retire or refine it. Preserve dated history and do not rewrite earlier versions to make predictions appear accurate.
24. For each future quest, re-read the latest protocol and prior evaluation ledger before topic selection, then run the red-team at least at **topic selection**, **after first success**, **before final archive**, and **before public publishing**. The protocol improves when feedback and actual outcomes are supplied; it is not an autonomous always-on agent or an automatic score guarantee.

### Permanent November Quest 3 failure correction

Observed planning error: after a single invitation-funded claim→send success, the researcher was ready to freeze publication. A direct shielded-faucet comparator had encountered UI gating/cooldown, and I treated the entire comparison as optional. This confused **one unavailable mechanism** with **no feasible alternative treatment**, prematurely weighted completion/website delivery over causal controls, and underweighted the user's explicitly stated evaluator-maximizing goal. The user had to prompt the stronger test.

Corrective rule: after the first successful payment, deliberately identify the top remaining untested competitor and try a feasible **public-faucet → public registration → transparent Shield → actual private send → separate recipient wallet confirmation** path, or the closest safe equivalent in a future context. Do not call two different funding routes identical independent repeats. November Quest 3 then verified a second real 3 RLS private send, observed the recipient's shielded balance increase from 3 to 6 RLS, authenticated public balance/fee trails, detected 38 additional forged-evidence cases and documented the unperformed direct shielded-faucet case. This is the *template* for proactive control-search, not a command to repeat the same test/topic every week.

**Nonnegotiable final gate: "Before I say DONE, which one additional feasible experiment would a strict evaluator most regret that I didn't run? What would it teach us? Have I tested an alternative when my first control was blocked? If no high-value feasible gap remains, freeze and release honestly."**
